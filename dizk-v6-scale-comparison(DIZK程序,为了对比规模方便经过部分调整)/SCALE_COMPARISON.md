# 相同约束规模的定义和报告口径

## 匹配什么

读取 v6 历史 CSV 的乘法门数 N 和线性关系数 Q，生成 N 条非线性 R1CS 与 Q 条线性 R1CS，总数 M=N+Q。两类数量分别匹配，不只匹配 N。

| 参考 MC | v6 乘法门 N | v6 线性关系 Q | DIZK 总约束 M |
| --- | ---: | ---: | ---: |
| 1 | 98,556 | 197,112 | 295,668 |
| 10 | 105,522 | 211,044 | 316,566 |
| 20 | 114,020 | 228,040 | 342,060 |
| 40 | 130,258 | 260,516 | 390,774 |
| 80 | 163,492 | 326,984 | 490,476 |
| 100 | 179,730 | 359,460 | 539,190 |
| 200 | 262,436 | 524,872 | 787,308 |
| 400 | 427,090 | 854,180 | 1,281,270 |

作者 QAP/FFT 路径把 M+2 向上补到二次幂。默认八点的 FFT domain 依次为 524,288、524,288、524,288、524,288、524,288、1,048,576、1,048,576、2,097,152。因此 MC=100、400 附近的成本可能发生阶跃，M 是实际约束数，FFT domain 是内部补齐规模，两者不能混写。

v6 的“门/关系”是在模 N² 中的原生运算单位；DIZK 的约束是在素域 Fr 中的运算单位。相同数量只提供规模控制，不代表一条约束的运算复杂度、密度、值域或密码学语义相同。MC 在 DIZK 中只是对应参考行的标签，不是已被 DIZK 证明的消息数量。

本版省去了原来的大整数 limbs、商/进位、位分解和模 N² 提升。因此上述规模远小于严格证明同一 Paillier 计算的规模。不能在论文中将这项规模缩减写成 Paillier 算法优化。

## 合成关系

使用作者 BN254b 的 Fr：

`p = 17855808334804902850260923831770255773646114952324966112694569107431857586177`

维护链中的最近两个值 x、y。乘法行约束 `(a*x+d)*(b*y+e)=z`；线性行约束 `(a*x+b*y+d)*1=z`，所有计算在 Fr 中。每行更新最近两个值。a、b、d、e 为确定生成的小系数，避开零状态。两类约束按 floor 比例分布在链中，数量精确相符，不加入空的 `0=0` 行。

索引 0 是常数 1，索引 1 是最终公开输出，索引 2 和 3 是初始私有值，中间输出索引 4 到 M+2。共 M+3 个变量，所有变量参与关系。`primary_inputs=2` 包含常数和最后输出，这与原 v6 的公开 Kq 数量不同。生成器的见证用于可重复的性能测试；不声称隐藏一个真实应用秘密。

生成器流式写入文本，避免在 Python 中构造百万行的对象列表。Java 导入后使用作者分布式 Setup/Prover/Verifier。计时前独立检查实际满足性、公开输出、实际 N/Q 分类、文件完整性和 scope；真实 Verify 为 false 的结果不会接受为成功性能数据。

## 参考实测与证据

`reference/v6_full_t16_r1.csv` 来自用户提交的 `v6_512_20261012T145100Z_OfoZn3.zip`。全部八点实际 Paillier 位数为 512、线程数为 16、次数为 1。原日志的 GoogleTest App.Run 完成；保存的 EndToEnd.cpp 在验证返回 false 时抛出异常，因此全程成功支持这些点的完整 ZKP 验证通过。旧 CSV 的 normal_verified=unknown 是该日志解析字段缺失，不能据此伪造逐密文解密核验。

SHA、环境信息和上述证据写入 `reference/provenance.json`。当前运行只重新测 DIZK；历史 v6 与新 DIZK 的运行日期、JIT、系统负载可能不同。做论文结论前，应在相同虚拟机配置和安静负载下重新采集基线，并增加重复次数。当前一次运行不输出置信区间。

自选参考表可以传 `--v6-csv PATH`。不具备已核对 provenance 的 CSV 只作为数量和时间参考，v6_verified 为 unknown。CSV 未记录线程/次数时，可用 `--reference-threads`/`--reference-repeat` 明确声明；报告记录其元数据来源是声明，不能把它当成日志验证的实测配置。不要把 DIZK 第2次配对到唯一的 v6 第1次；需要对应重复编号的基线。

## 时间列

- `v6_proof_generation_seconds = commit_s + prove_s`，包含原日志中完整 commitment 与证明生成阶段。
- `dizk_prove_seconds` 为作者 Prover 路径；比值是它除以上项。
- Setup 独立列出，因为 DIZK 的 circuit-specific trusted setup 与 v6 的预处理机制不同。
- Verify 独立列出；输入生成、读取、RDD materialize、独立满足性检查、Spark 启动不混入 Prover。
- 阶段之和不自动等于进程端到端时间；实际总任务/驱动墙钟也保留。
- RSS 只报告实测 `/usr/bin/time` 数据，Java Xmx 是上限设置，不能代替实测峰值。

可在论文中写：“在单机虚拟环境下，构造与原实验乘法/线性约束数量一致的 BN254b 合成 R1CS，测量 DIZK 的证明成本，并与历史 v6 记录作规模对照。”应同时披露“不同计算关系、算术域、拓扑、公开输入和证明机制”。不要写“DIZK 复现了同一 512-bit Paillier 任务”或把比值称为本项目的并行加速比。

## 失败和成功

每点有自己的验证结果和成功标记。根标记 `SCALE_BENCHMARK_COMPLETE.txt` 只在全部指定点成功后写出。没有该标记时，已完成点可用于调试和资源观察，不能当作完整八点实验。输入被篡改、未完成目录、scope 混入、错误约束数量、NaN/无穷计时、验证失败均应拒绝汇总为完整实验。
